# SOP — Weekly Client Reporting

| | |
|---|---|
| **Purpose** | Produce and send a weekly report that a busy client can read in 90 seconds and act on without a follow-up question. |
| **Owner** | Virtual Assistant |
| **Frequency** | Weekly — Friday, sent before 16:00 client time |
| **Time required** | 30 minutes once the template is set up |
| **Last reviewed** | 2026-09-01 |

---

## Why this exists

Most VA reporting fails in one of two directions. Either it is a list of
everything done, which the client will not read, or it is "all good this week!",
which tells them nothing and quietly erodes their sense that anything is happening.

A good weekly report does three jobs: it proves the hours, it surfaces decisions
the client needs to make, and it removes the need for them to ask "where are we?"

**The report is also the rate argument.** A client who can see the work is a
client who renews.

---

## Prerequisites

- [ ] Time log or task tracker kept current through the week (not reconstructed Friday)
- [ ] Reporting template built and agreed with the client during onboarding
- [ ] Agreed send day, send time, and recipients
- [ ] Access to whatever the metrics come from

---

## Steps

1. **Thursday: keep the running notes current.** Add to the draft as the week
   happens. Reconstructing five days from memory on Friday afternoon is where
   errors and vagueness come from.

2. **Friday 14:00 — pull the numbers.** Refresh the source data first, then read
   the figures. Never type a number into the report by hand; link or paste it from
   the source, so there is one place to correct if it is wrong.

3. **Write the four sections, in this order.** Order matters — the client reads
   top-down and often stops early.

   **a. Decisions needed from you** *(put this first, always)*
   Each item: what the decision is, the options, your recommendation, and the
   date it becomes blocking. If there are none, write "None this week" — do not
   omit the section, or its absence stops being informative.

   **b. Done this week**
   Grouped by outcome, not chronologically. Three to six bullets. "Cleared the
   invoice backlog — 62 documents filed, inbox at zero" beats six separate lines
   about filing.

   **c. In progress / next week**
   What is moving, what lands when. Flag anything at risk *before* it slips.

   **d. Numbers**
   The two or three metrics agreed at onboarding. Same metrics every week, in the
   same order. Changing the metric set is how a report loses its ability to show
   a trend.

4. **Apply the 90-second test.** Read it as though you are the client and have not
   thought about this work all week. If anything needs a second read, rewrite it.
   Cut every sentence that does not change what they will do.

5. **Check before sending:**
   - [ ] Every number traced back to its source, not typed from memory
   - [ ] No unexplained jargon or internal shorthand
   - [ ] Every blocker names who it is waiting on and since when
   - [ ] Attachments actually attached; every link opened and checked
   - [ ] Recipients correct, including the backup contact

6. **Send before 16:00 client time.** A report landing after the client's Friday
   is a report read on Monday, by which point the decisions have aged a weekend.

7. **File a copy** in `03-reporting/` as `YYYY-MM-DD-weekly.pdf`. This archive is
   the evidence base for the rate conversation at renewal.

---

## Edge cases

| Situation | What to do |
|---|---|
| A quiet week with little to show | Send it anyway, honestly. "Quiet week — routine processing, no blockers" is a legitimate report. Padding it is how a report stops being trusted. |
| Something went wrong this week | Lead with it in section (a). State what happened, the impact, what you did, and what prevents a repeat. Never let a client discover a problem from somewhere else. |
| Data source is down on Friday | Send on time with the section marked "pending — source unavailable, will follow Monday", then actually follow up Monday. Do not delay the whole report for one metric. |
| Client never responds to the report | Keep sending. Ask once at the next call whether the format is useful and what they would cut. Silence usually means it is fine, not unread. |
| Client asks for a metric that cannot be measured reliably | Say so plainly, propose the closest thing that *is* reliable, and note the difference. A confident wrong number is worse than an honest gap. |
| A public holiday falls on the send day | Send the working day before. Agree this once, at onboarding, rather than deciding each time. |

---

## Escalation path

1. **A blocker unresolved for two consecutive reports** → raise it directly by
   email rather than letting it repeat silently in the report.
2. **A metric moving the wrong way two weeks running** → flag it explicitly with a
   proposed diagnosis. Do not let a trend hide inside a table.
3. **An error discovered in a report already sent** → send a correction the same
   day, with the corrected figure and one line on the cause. Do not wait for the
   next report and do not quietly fix it in the archive.

---

## Definition of done

- [ ] Report sent before the agreed time
- [ ] All four sections present, decisions section first
- [ ] Every figure traceable to a source
- [ ] Copy filed in `03-reporting/`
